## Claim a node and admit users (planned)

Bound to [Phase 10 user claims and node administration](../../ROADMAP.md#user-claims-and-node-administration). The original discovery release left Claim disabled. Claim is now available from discovered worker details using saved identities. Preserve offline use and the existing interface allowlist.

1. **Set up the person.** After the node-key step, resolve the local user signing identity independently of the device key. Support recovering the same user on another device. Prompt for a screen name only if missing, offer the equivalent local setup for a human using the CLI, and persist it in the local SQLite profile. An unattended worker needs no fabricated user. Settings can rename the user. Validate length, whitespace and control characters. Permit duplicate and changed names. Use the user-key fingerprint as the stable identifier in grants, future chat and scores. Show a short fingerprint alongside ambiguous names in administration.
2. **Make Claim one user action.** From the discovered host detail, confirm the target node fingerprint by comparison with the worker console or trusted SSH. Use HTTPS on an approved network/interface. The worker serves `GET /v1/auth/challenge` and `POST /v1/auth`. The final JSON includes the claimant’s user public key, screen name, originating hostname and node public key, target node and intended cluster IDs, challenge ID and signatures. Use a short-lived, unpredictable single-use challenge. Bind proof to the protocol version, operation, recipient and submitted metadata using a specified byte encoding; verify user and device possession separately. Return JSON on every outcome. Only public data and proofs cross the network. Existing device enrollment, certificate issuance and cluster authority checks still govern binding the target to the selected cluster. A later registration cannot move an already-claimed host.
3. **Commit the first admin exactly once.** Store node-local user records in SQLite keyed by user fingerprint, with display metadata, role, access state and audit timestamps. Keep the initial claimant fingerprint and cluster binding durable. In one transaction recheck admission policy, consume the challenge, verify eligibility for initial claim and record the outcome. Only the personal identity confirmed on the worker can become the first approved admin with access to all services offered by that node. Later distinct users start pending with zero service access. A repeated proof cannot replay; a fresh proof from the same user returns the existing record without duplicate notices or changed privileges. A blocked key stays blocked. Restart, demotion and deletion must never reopen first-admin election.
4. **Enforce decisions at the node.** A verified user can establish a short-lived authenticated session and inspect their own status. Check current node-local approval and scope on every protected service call; require current admin authority for administrative changes. Cluster → node detail lists authenticated users, screen names, fingerprints, role and pending/approved/blocked status. Admins approve access, block it, promote approved users to admin, and demote admins. A block invalidates active access and pending credentials. Preserve at least one approved admin, and recover lost admin credentials through an owner-local process. Record administrative changes without logging credentials or private payloads.
5. **Open or close new registrations.** Give admins a persistent switch on that node’s Cluster screen. Closing stops first-time proofs from creating new user records, approval notices or pending clutter, including challenges issued before closing. Returning known users can still authenticate under their existing policy. Existing pending users stay pending and blocked users stay blocked. Opening or closing registration does not alter listeners, network grants or independently exposed provider APIs. Document whether each service is reachable directly; where Apparat approval must govern all access, require a private provider listener or equivalent provider-side enforcement.
6. **Reuse the name deliberately.** Future chat shows the current screen name of the authenticated sender. On first eligible STMPCK score submission, ask whether to publish scores with this screen name. Default to local scores until affirmative opt-in. Keep leaderboard participation and screen-name editing in Settings. Declining creates no public score or repeated prompt; switching it off stops future submissions. Define treatment of previously published entries before enabling publication.
7. **Test the whole path.** Race two first claims and verify exactly one approved admin. Cover copied public keys, expired/replayed proofs, changed hostname/name/target/cluster, duplicate names, duplicate registrations, restart, blocked-user retry and last-admin protection. From two real clients demonstrate pending denial, approval and service use, promotion and admin action, immediate block, closed admission and known-user reauthentication. Verify that renaming preserves grants, a declined leaderboard prompt sends nothing and a new device using the same user key retains its identity. Exercise screen-name onboarding, accessible Cluster controls and action-catalog availability on narrow and wide layouts.

**Shipped bootstrap decision.** On the host console or through trusted SSH, inspect the worker fingerprint with `apparatd trust-host` and confirm the intended personal fingerprint with `apparatd trust-host OWNER_FINGERPRINT`. Compare the worker identity at first connection. Subsequent connections pin the signing key across leaf renewal. A different signing key requires manual review on the client. Existing workers also need local owner confirmation before exposing provider operations. The installed worker’s owner was matched to the existing desktop identity before the private-clone acceptance test.

For implementation checkpoints, run checkout identity before edits, package and race tests through the build gate, documentation and navigation checks, then the canonical no-flag build. Record eligible artifacts and GitHub readback. Record physical Pixel validation as pending if unavailable. Promote local functionality independently of later cluster work. Close the full plan when each claimed platform and network behavior has acceptance evidence or an explicitly recorded deferral.
